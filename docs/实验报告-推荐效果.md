# 实验报告：番剧推荐方案设计与离线效果评测

> 论文对应章节：第 4 章「推荐模块设计」+ 第 6 章「推荐效果实验」。
> 现状先说清楚：**本系统目前没有独立的推荐算法服务**，首页「热门推荐」是按播放量/评分的热榜，AI 桌宠的「推荐我可能喜欢的」本质是关键词检索 + 大模型组织语言（见 `abc-ai-service/src/main/java/com/abc/aiservice/feign/UserFeignClient.java:16` 的注释自述：「实际上只能靠问题关键词搜番剧，谈不上画像」）。
> 因此本报告 = 「可落地的推荐方案设计 + 可复现的离线评测方法」；若时间允许，按 §5 实施后把实测数字补进 §4 的表格。

## 1. 为什么值得做（答辩价值）

1. 微服务项目里「多一个算法模块」比「多一个 CRUD 服务」更能体现工作量与深度；
2. 推荐是**可量化**的：命中率、NDCG、覆盖率都能与基线对比，实验章节天然成立；
3. 能复用已有数据资产：`watch_history`（观看）、`rating`（评分）、`user_favorite`（收藏/追番）、`search_history`（意图），这些表已经在库里。

## 2. 数据基础核查（决定算法能做成什么样）

### 2.1 可用信号

| 表 | 字段 | 推荐中的角色 | 证据 |
| --- | --- | --- | --- |
| `watch_history` | user_id, episode_id, anime_id, progress, watched_at | 隐式反馈（看过=正样本，progress 可做置信度） | `sql/abc_anime.sql` 的 `CREATE TABLE watch_history` |
| `rating` | 用户对番剧的评分 | 显式反馈（1–10 分），比隐式更可信 | `sql/abc_anime.sql` |
| `user_favorite` | user_id, anime_key, status（1 想看/2 在看/3 看过/4 弃番）, is_follow | 强意图 + 可做「弃番」负反馈 | `sql/03_platform_extension.sql:12-28` |
| `search_history` | keyword, norm_keyword, result_count, source | 冷启动兴趣（无行为新用户） | `sql/03_platform_extension.sql:31-42` |
| `anime` / `anime_tag` / `tag` | 标题、评分、年份、类型、标签 | 内容侧特征，解决物品冷启动 | `sql/abc_anime.sql` |

### 2.2 现实约束（必须写进论文，别假装数据很多）

- 本系统真实用户与行为量小，单机自采数据不足以训练矩阵分解；
- 因此离线评测采用**双轨**：① 用公开数据集（Bangumi Archive 的收藏数据）验证算法实现正确性；② 用本系统库内真实小样本做端到端链路验证（能跑通、接口能出结果）。

公开数据来源（外部资料）：`bangumi/Archive` — <https://github.com/bangumi/Archive>（Bangumi 用户收藏/评分 的公开归档，字段含用户 id、条目 id、评分、收藏类型），可用于构造 user-item 交互矩阵做离线评测。使用时注意遵守其仓库声明，只在论文中引用统计结论，不再分发原始数据。

## 3. 方案设计：三路召回 + 一路融合（Java 实现，不引入新中间件）

```
                  ┌─────────────────────────┐
                  │  推荐接口 /api/anime/recommend  │
                  └───────────┬─────────────┘
                              │ userId 为空→热榜兜底
              ┌───────────────┼───────────────┐
              ▼               ▼               ▼
        itemCF 召回       内容标签召回       热榜/新番召回
      (看过的人还看)     (同 tag/同类型)     (冷启动 & 多样性)
              └───────────────┼───────────────┘
                              ▼
                     加权融合 + 去重 + 打散
                              ▼
                  写 user_recommend 表 + Redis 缓存
```

### 3.1 itemCF（主算法，Java 可手写，不依赖 Mahout/Spark）

- 交互矩阵：`user × anime` 隐式评分 `w = 1（看过） + 0.5（看完 progress≥90%） + 2（评分≥8） - 2（弃番）`；
- 相似度：余弦 `sim(i,j) = Σ_u w(u,i)·w(u,j) / (||w(·,i)||·||w(·,j)||)`；
- 预测分：`score(u,j) = Σ_{i∈N(u)} sim(i,j) · w(u,i)`，取 Top-K 邻居（K=20）；
- 工程实现：一次性把交互矩阵读进内存（万级用户 × 千级物品完全放得下），用 `HashMap<Long, Map<Long, Double>>` 稀疏存储，相似度只对「共同用户数 ≥ 2」的物品对计算，复杂度 O(Σ_u |N(u)|²) 可控；
- 定时任务：每天凌晨跑一次（`@Scheduled(cron = "0 30 3 * * ?")`），结果写 `user_recommend`，接口只读表/缓存，保证响应时间。

### 3.2 内容召回（解决物品冷启动 + 提升可解释性）

- 特征：`anime_tag` 的标签集合 + `anime.type/year/rating_avg`；
- 打分：用户历史番剧标签分布的 TF-IDF 加权（标签在全体番剧中越稀有，权重越高）；
- 输出带「理由」：`因为你喜欢【热血/战斗】`，前端可直接展示，这也是答辩演示的加分项。

### 3.3 融合与重排

- 归一化后加权：`0.6·itemCF + 0.3·内容 + 0.1·热度`（权重可配，便于做对照实验）；
- 过滤：已看过、已弃番、已收藏；
- 打散：同标签连续不超过 2 个，避免「一屏全是异世界」。

### 3.4 新增表（DDL 草案，由 Lead 统一并入 `sql/`）

```sql
CREATE TABLE `user_recommend` (
  `id`         BIGINT NOT NULL AUTO_INCREMENT,
  `user_id`    BIGINT NOT NULL COMMENT '用户ID',
  `anime_id`   BIGINT NOT NULL COMMENT '番剧ID',
  `score`      DOUBLE NOT NULL COMMENT '融合分',
  `reason`     VARCHAR(64) DEFAULT NULL COMMENT '推荐理由（标签/相似番剧名）',
  `source`     VARCHAR(16) DEFAULT 'CF' COMMENT 'CF/CONTENT/HOT/HYBRID',
  `batch_no`   VARCHAR(20) NOT NULL COMMENT '批次号 yyyyMMdd',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_user_anime_batch` (`user_id`,`anime_id`,`batch_no`),
  KEY `idx_user_batch` (`user_id`,`batch_no`,`score`)
) COMMENT='离线推荐结果表';
```

### 3.5 接口设计

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/anime/recommend?size=12` | 登录用户读 `user_recommend`（带 `X-User-Id`），未登录/无结果回退热榜 |

## 4. 离线评测方案（可直接复现）

### 4.1 数据集与切分

- 数据集 A（实现校验）：Bangumi Archive 公开收藏数据，过滤交互数 ≥ 5 的用户；
- 数据集 B（本系统）：从 `watch_history` + `rating` 导出的 user-anime 交互（规模小，仅验证端到端）；
- 切分：留一法（每个用户最后一次交互作测试集，其余训练），负样本采样 100 个未交互物品。

### 4.2 指标

| 指标 | 定义 | 为什么选 |
| --- | --- | --- |
| HR@10 | 命中率：Top-10 里是否含测试物品 | 直观、答辩好讲 |
| NDCG@10 | 考虑排序位置 | 比 HR 更能区分算法优劣 |
| Coverage | 推荐结果覆盖的物品占比 | 防止「只推热门」 |
| 新颖度 | 推荐物品平均热度分位 | 说明不是纯热榜 |

### 4.3 对照组

| 组 | 说明 |
| --- | --- |
| Random | 随机推（下界） |
| MostPopular | 按播放量/评分排序（当前首页就是这么做的，是必须打败的基线） |
| ContentTag | 纯标签 TF-IDF |
| ItemCF | 本文主算法 |
| Hybrid | 三路融合 |

### 4.4 结果表模板

## 5. 实施路线（按剩余时间排优先级）

## 6. 风险与替代方案

| 风险 | 影响 | 替代 |
| --- | --- | --- |
| 真实数据太少，指标无意义 | 实验章节单薄 | 用 Bangumi Archive 公开数据做主评测，本系统只做链路验证 |
| 全量 itemCF 内存/耗时 | 离线任务跑不动 | 缩小到「近 90 天活跃用户」；或只算相似度 Top-50 邻居 |
| 与 AI 桌宠推荐职责重叠 | 答辩被问「到底哪个算推荐」 | 明确分工：AI 负责「对话式解释与交互」，推荐服务负责「候选生成」，AI 的候选由推荐接口提供（可作为一个改进点写进展望） |

## 7. 结论（未实施时也能写进论文的版本）

本文分析了系统内可用的四类行为信号（观看、评分、收藏、搜索），设计了「itemCF + 内容标签 + 热榜」三路召回、加权融合与规则重排的推荐方案，并给出了留一法 + HR/NDCG 的离线评测协议与五组对照实验。
当前系统已具备全部数据基础与接口扩展点，推荐服务作为独立演进方向在「不足与展望」中说明；若在答辩前完成 P0–P2，则将实测指标补入 §4.4。
