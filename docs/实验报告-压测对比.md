# 实验报告：性能压测与改造前后对比

> 论文对应章节：第 6 章「系统测试」6.x 性能测试与对比实验。
> 压测脚本、参数说明、首次运行检查清单见 `jmeter/README.md`；脚本本体是 `jmeter/rest-test.jmx`、`jmeter/danmaku-test.jmx`、`jmeter/run.ps1`。
> 本文件负责：**实验设计、指标口径、结果表、结论写法**。结果表在未实跑前保持空白——不编数据是底线。

## 1. 测试目标

回答三个问题：

1. 系统在多少并发下还能保持可用（容量基线）；
2. 本轮的异步化/缓存/限流改造，到底带来了多少提升（改造前后对比）；
3. 瓶颈在哪（WS 广播扇出、Mongo 写、网关鉴权还是 Redis）。

## 2. 测试环境（必须与结果一起写进论文）

| 项 | 值 |
| --- | --- |
| 压测机 | 与压测目标同机（避免网络成为噪声），CPU/内存型号填实际值：`Get-CimInstance Win32_Processor`、`Get-CimInstance Win32_ComputerSystem` |

| JMeter | 5.6.x + `jmeter-websocket-samplers` 插件（见 `jmeter/README.md` 的环境准备） |
| 观测 | `docker stats --no-stream`、服务 INFO 日志（弹幕 flush 统计行）、MongoDB `countDocuments` |

## 3. 场景设计

### 3.1 场景一：REST 读多写少（`rest-test.jmx`）

- 线程组 `01 匿名浏览链路`：`/api/anime/list`、`/api/anime/hot`、`/api/search/anime`、`/api/anime/{id}`、`/api/danmaku/list`，比例均衡，思考时间 300 ms；
- 线程组 `02 登录+个人中心链路`（默认禁用）：登录拿 token → `/api/user/profile`，用于验证鉴权链路开销；
- 档位：50 / 100 / 200 线程（`run.ps1` 会对 REST 场景自动减半，实际压力按 `-Levels` 的一半算，避免压测机先被打满）。

### 3.2 场景二：弹幕 WebSocket（`danmaku-test.jmx`）

- 每个线程：建立 WS 连接 → 每 300 ms 发一条弹幕 → 读一条广播；
- 档位：200 / 500 / 1000 并发连接，持续 120 s；
- 注意这是**单房间广播**模型：N 个连接下每条弹幕产生 N 次发送（N² 扇出），1000 并发时的理论发送量是 200 并发时的 25 倍，这一条要在论文里点明，否则数据看起来「不合常理」。

### 3.3 执行

```powershell
# 全场景：200/500/1000 三档，每档 120 s
.\jmeter\run.ps1 -Scenario all -Levels 200,500,1000 -Duration 120 -Ramp 10

# 单场景冒烟
.\jmeter\run.ps1 -Scenario rest -Levels 50 -Duration 30
```

输出：`jmeter/results/<场景>-<线程数>/` 下的 HTML 报告 + `.jtl`，以及 `jmeter/results/summary.csv`、`summary.md`（`run.ps1` 的 `Get-JtlMetrics` 自动汇总 TPS/P95/错误率，可直接贴表）。

## 4. 指标口径（避免答辩被问口径不一致）

| 指标 | 口径 |
| --- | --- |
| TPS | 该 label 的 `样本数 / (最后时间戳 − 首时间戳)`（秒）；同一场景多 label 分别统计，不求和 |
| 平均 / P95 | JMeter 采样 `elapsed`（ms），**不含** ConstantTimer 的思考时间；P95 = 升序第 ⌈0.95n⌉ 个 |
| 错误率 | `success != true` 占比（WS 场景含握手失败） |
| CPU | `docker stats` 采样，取压测稳定段 3 次平均 |
| 落库条数 | `db.danmaku.countDocuments({})` 前后差值，与发送条数对比（差额应等于限流+去重拦截数） |

## 5. 改造前后对照项（可配置开关的才可做对照）

| # | 对照项 | 改造前（对照组） | 改造后（实验组） | 切换方式 | 预期 |
| --- | --- | --- | --- | --- | --- |
| 1 | 弹幕落库方式 | 本地批量落库（`DANMAKU_MQ_ENABLED=false`，默认） | RocketMQ 异步（`true`） | `docker-compose.yml` 环境变量 | 高并发下 flush 线程耗时下降；单机低并发可能无差异 |
| 2 | 弹幕限流 | 关闭（`danmaku.rate.max-per-window` 调到 1000000） | 开启（默认 20 条/60 s） | `application.yml` 或环境变量 | 开启后错误率上升（预期行为），但服务不被刷爆 |
| 3 | 弹幕去重 | `danmaku.dedup.enabled=false` | `true` | 同上 | 去重开启后广播量下降；单条延迟不变 |
| 4 | 时间窗 L1 缓存 | 需先加 `danmaku.local-cache.enabled` 开关（当前只有 TTL/容量，无总开关）——**P1 待实现** | 开启 | 配置 | 重复时间窗查询的 P95 明显下降 |
| 5 | 网关黑名单本地短缓存 | 未实现（每请求查 Redis）——**P1 待实现** | 本地 TTL 1 s 缓存 | 代码 | 高频鉴权接口 P95 下降；代价是登出延迟最多 1 s 生效 |
| 6 | 搜索实现 | MySQL LIKE 聚合（默认路由到 anime-service） | Elasticsearch（改网关路由到 search-service） | 改 `abc-gateway` 路由 | ES 在关键词相关性上更好，但冷启动与内存代价高 |

> 表里第 4、5 项是「设计好了但没做」的对照，答辩时如实说明，并把它们写进「后续工作」。不要拿不可切换的项（例如「同步广播 vs 线程池广播」）编造对照数据。

## 7. 预期与解释（写结论时的安全话术）

- 「REST 场景 TPS 主要受限于 MySQL 连接池与 Redis 往返，网关鉴权引入的额外延迟在 x ms 量级」——需要用「直连服务 vs 走网关」两组数据支撑；
- 「弹幕场景随并发增长，TPS 不升反降是 N² 扇出的必然结果，说明瓶颈在广播而非落库；可通过分片广播/房间活跃度降采样优化」；
- 「MQ 开启后 flush 线程耗时从 x ms 降到 y ms，但端到端 P95 变化不大——因为落库本来就不在请求线程上，MQ 的收益是**解除 flush 线程与 Mongo 的耦合**，使单轮 flush 不再受 Mongo 抖动影响」，这个解释比硬吹「MQ 提升 xx%」更站得住；
- 若某档出现大量错误，先分类：连接被拒（端口/线程数）、超时（GC/线程池满）、业务 4xx（参数/鉴权）——论文里给错误分类饼图比只写「错误率 3%」更有说服力。

## 8. 已知限制

1. 脚本未在安装 JMeter 的机器上实跑过（本环境无 JMeter），首次运行按 `jmeter/README.md` 的检查清单逐项确认；
2. 压测机与被测系统同机，CPU 争抢会压低绝对值，但对照实验的相对结论仍有效；
3. 单 Broker、单弹幕实例，无法验证「多实例消费」的扩展性；
4. AI 服务依赖外部大模型 API，不纳入压测（会引入不可控外部延迟）；
5. 测试数据是构造的，与真实用户行为分布不同，结论只用于容量规划与改造对比。

## 9. 结论模板（跑完后填数字）

本草对系统进行了 REST 与 WebSocket 两类压测。REST 场景在 x 并发下 TPS 达到 y、P95 为 z ms；弹幕场景在 1000 并发连接下保持错误率 w%，落库条数与发送条数偏差 v%（来自限流与去重拦截）。
对照实验表明，RocketMQ 异步落库使单轮 flush 耗时由 a ms 降至 b ms；限流与去重开关对错误率与广播量的影响符合设计预期。
瓶颈分析表明当前主要限制为单房间广播的 N² 扇出与单实例消费，后续可通过广播分片与水平扩容改进。
