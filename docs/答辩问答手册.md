# 答辩问答手册（22 问）

> 用法：先看「一句话回答」把结论说清，再看「展开」补细节。带 `文件:行号` 的地方建议现场打开 IDE 展示，比口头描述可信。
> 原则：**已实现的讲实现，没实现的讲取舍**。被问到没做的东西，回答「没做 + 为什么 + 打算怎么做」远好于硬编。

## 一、架构与拆分

### Q1 为什么用微服务？单体不是更简单吗？

**一句话**：这个项目的业务边界天然是分裂的（番剧元数据、弹幕实时流、视频源解析、AI 对话），它们的读写特征和伸缩需求完全不同，拆开能让「弹幕这种 IO 密集 + 高并发」的部分独立扩容，也符合毕设要考察的分布式能力。

**展开**：
- 弹幕是长连接 + 高写入，番剧元数据是读多写少 + 强关系，放一个进程里线程池/连接池会互相抢；
- 10 个服务的划分依据是「业务能力 + 数据所有权」，每个服务只操作自己的库表，跨服务用 Feign 或网关聚合；
- 代价我也清楚：分布式事务、链路排查、部署复杂度都上升——这些在「不足与展望」里写了，并且用 Nacos + 网关 + 统一返回把复杂度压住了一部分。

### Q2 10 个服务是不是拆得太细？边界怎么定的？

**一句话**：按「谁拥有这份数据、谁承担这类流量」来定，不是为了数量好看。

**展开**：
- `auth` 拥有凭证与 token 生命周期；`user` 拥有用户资料与行为；`anime` 拥有番剧/剧集元数据；
- `danmaku` 独立是因为它是唯一的 WebSocket 长连接服务 + MongoDB 存储 + 可选 MQ；
- `source` 独立是因为它要跑 Jsoup 解析第三方页面，属于「不可信外部 IO」，隔离出去避免拖累主链路；
- `search` 独立是为了让 ES 版本可以按需启停（网关默认走 `anime-service` 聚合搜索，见 `abc-gateway/src/main/resources/application.yml:31-35`）。

### Q3 Nacos 在项目里到底做了什么？

**一句话**：两件事——服务注册发现（`lb://` 路由靠它解析实例）和配置中心（共享的 Redis/MySQL 配置由它下发）。

**展开**：
- 各服务 `bootstrap.yml` 里配了 `spring.cloud.nacos.config`，`file-extension: yaml`，并引用共享配置 `abc-common.yaml`、`abc-datasource.yaml`（例：`abc-user-service/src/main/resources/bootstrap.yml:4-19`）；
- 共享配置内容在 `sql/nacos/abc-common.yaml`（Redis 连接）与 `abc-datasource.yaml`（MySQL 连接）；
- 容器化时用一次性作业 `nacos-config-init` 把「host=127.0.0.1」的共享配置替换成容器服务名再发布（`docker-compose.yml:245-261`），业务代码一行不改——这是答辩可以讲的「配置中心不是摆设」。

### Q4 网关做了哪些事？鉴权为什么放在网关？

**一句话**：路由 + JWT 校验 + 身份头注入 + 黑名单拦截 + 统一错误体，一处实现全站生效。

**展开**：
- 全局过滤器 `JwtAuthGlobalFilter`（`abc-gateway/src/main/java/com/abc/gateway/filter/JwtAuthGlobalFilter.java`），`getOrder()=-100` 保证最先执行（`:217-219`）；
- 白名单分两类：完全公开（登录/注册/WS/文档）`PUBLIC_ALL`（`:55-64`）与匿名只读（番剧浏览、弹幕列表、评论查看）`ANONYMOUS_GET`（`:70-84`），这样「游客能看番但不能发弹幕」不用在每个服务里判；
- 校验通过后注入 `X-User-Id / X-Username / X-Role` 三个头，下游服务直接信任（网关同时会先删掉客户端伪造的同名头，`:106-111`）。

### Q5 如果有人绕过网关直接访问服务端口呢？

**一句话**：这是当前设计的已知弱点——服务端口在 compose 里也映射到了宿主机（8081–8089），生产环境应当只暴露网关，或用内网 network + 令牌校验。

**展开**：
- 网关已经预留了 `X-Internal-Token` 常量（`JwtAuthGlobalFilter.java:46-50`），但下游服务尚未强制校验，属于「设计到位、实现未完成」；
- 生产做法：服务只监听容器内网、compose 不映射端口，或引入 mTLS/内部签名；
- 答辩时说清这是取舍：毕设为了「方便评审直接调接口」保留了端口映射，并给出加固方案。

## 二、认证与安全

### Q6 为什么用双 Token？access token 过期了怎么办？

**一句话**：access 短命（默认 2 小时量级）+ refresh 长命（7 天），前端用 refresh 静默续期，避免用户频繁重登。

**展开**：
- 登录返回 `TokenDto`（accessToken/refreshToken/expiresIn/userId/username/role），见 `abc-common/src/main/java/com/abc/common/dto/TokenDto.java`；
- refresh token 存 Redis `refresh_token:{userId}`（`abc-auth-service/.../AuthServiceImpl.java:121-122`），天然支持「单端登录」：重新登录覆盖旧值，旧 refresh 立即失效；
- 续期接口 `POST /api/auth/refresh`（`AuthController.java:59`）。

### Q7 登出后旧 token 为什么立即失效？

**一句话**：登出时把当前 access token 写进 Redis 黑名单，网关每次请求都查一次。

**展开**：
- 写入：`blacklist:{token}`（`AuthServiceImpl.java:147-153`），TTL 设为该 token 的剩余有效期，不会无限膨胀；
- 校验：网关 `JwtAuthGlobalFilter.java:180-187`，用 `Mono.fromCallable(...).subscribeOn(boundedElastic)` 包住阻塞的 Redisson 调用，避免阻塞 Netty 事件循环；
- 可用性取舍：Redis 异常时 `onErrorResume` 降级为「不拦」，即宁可短暂放宽也不让全站 401。

### Q8 前端把 token 存哪？XSS 了怎么办？

**一句话**：当前存 localStorage（`abc-frontend` 的请求拦截器统一加 `Authorization`），XSS 风险靠「不用 v-html 渲染用户输入 + 后端转义」控制。

**展开**：
- 更安全的方案是 HttpOnly Cookie + CSRF token，但跨域与 WebSocket 握手会变复杂，本项目选择「localStorage + 短 access 有效期」；
- 弹幕/评论内容在后端做了归一化与正则屏蔽（`DanmakuContentGuard`、`danmaku.shield.patterns`，`abc-danmaku-service/src/main/resources/application.yml:40-44`），前端不做 HTML 注入。

### Q9 怎么防刷弹幕 / 恶意请求？

**一句话**：三层——网关白名单与角色、弹幕服务频率限制（60 秒 20 条）、5 秒内容去重 + 正则屏蔽。

**展开**：
- 频率限制用 Redis `INCR danmaku:rate:{userId}:{window}`，键定义在 `util/DanmakuKeys.java:18-19`，参数 `danmaku.rate.window-seconds=60 / max-per-window=20`（`application.yml:32-35`）；
- 去重：同房间 5 秒内相同归一化文本合并为「原文 xN」（`application.yml:36-39` + `service/DanmakuDedupService.java`）；
- 屏蔽：命中正则则落库标 `blocked=true` 且不广播，便于事后审计（`application.yml:40-44`）。

### Q10 视频源解析会不会被拿来做 SSRF / 打别人网站？

**一句话**：有风险，当前靠「规则由管理员配置（`/api/datasource/**` 仅 ADMIN）+ 流代理只转发白名单协议」限制，但完整的 SSRF 防护（内网 IP 黑名单、DNS 重绑定校验）没做，是已知不足。

**展开**：
- 管理接口在网关强制 ADMIN（`JwtAuthGlobalFilter.java:87-90`、`:152`），普通用户不能新增规则；
- 加固方向：解析目标 URL 时校验协议只允许 http/https、解析后的 IP 不在私有网段、限制重定向次数与响应大小；
- 答辩时把这条列为「安全加固计划」，比假装没问题更好。

## 三、数据与中间件

### Q11 Redis 在项目里承担了哪些职责？

**一句话**：缓存、计数、缓冲、索引、黑名单、限流、去重，七类用途，键都有命名规范。

**展开**（可直接背这张表）：

| 用途 | 键 | 位置 |
| --- | --- | --- |
| 登出黑名单 | `blacklist:{token}` | 网关 `JwtAuthGlobalFilter` |
| 单端登录 | `refresh_token:{userId}` | `AuthServiceImpl` |
| 验证码 | `captcha:{key}` | `AuthServiceImpl` |
| 热搜榜 | `search:hot`（ZSet） | `SearchController` |
| 热门缓存 | `anime:hot:{limit}`、`anime:episodes:{bgmId}` | `AnimeServiceImpl` |
| 弹幕缓冲 | `danmaku:buffer:{animeKey}:{ep}`（List） | `DanmakuBufferService` |
| 弹幕时间索引 | `danmaku:zset:{animeKey}:{ep}`（ZSet） | `DanmakuDispatchService` |
| 限流/去重 | `danmaku:rate:*`、`danmaku:dedup:*` | `DanmakuRateLimiter`、`DanmakuDedupService` |

### Q12 弹幕为什么用 MongoDB？MySQL 不行吗？

**一句话**：弹幕是「按集查询、只追加、无事务、量大」的典型场景，Mongo 的文档模型 + 批量插入比 MySQL 的 B+ 树插入更合适，也省掉分库分表的复杂度。

**展开**：
- 单集弹幕数可达数千到数万，MySQL 单表过亿后必须分片；Mongo 用 `animeKey + episodeNum` 做复合查询即可；
- 写入侧用 `insertMany` 批量（`service/DanmakuDispatchService.java`），配合 Redis 缓冲，写入次数降低两个数量级；
- 取舍：Mongo 无跨集合事务，本场景不需要；统计类需求（弹幕总量）用 ZSET 或计数表补。

### Q13 弹幕高并发怎么扛住的？

**一句话**：`onMessage` 只做校验 + Redis RPUSH，落库交给每秒一次的批量任务，广播交给独立线程池——请求线程恒定 O(1)。

**展开**：
- 写路径：`DanmakuWebSocketServer`（onMessage 极薄）→ `DanmakuBufferService`（Redis List，另用 Set 记录有积压的房间避免 KEYS 扫描）→ `DanmakuFlushTask`（`@Scheduled(fixedDelayString=...)` 每秒 LMPOP 批量取，`:70-99`）→ `DanmakuDispatchService`（先落库 → 建 ZSET → 失效缓存 → 广播）；
- 为什么 `fixedDelay` 不是 `fixedRate`：上一轮没跑完不能叠加，否则并发 drain 会打乱顺序（源码注释 `DanmakuFlushTask.java:37-38`）；
- 广播：`DanmakuBroadcaster` 用独立线程池 + `synchronized(session)`（Tomcat 不允许并发写同一 session），单条失败只记 DEBUG，不拖垮整批。

### Q14 RocketMQ 是不是硬需求？MQ 挂了系统还能用吗？

**一句话**：MQ 是可选链路，挂了自动降级为本地批量落库，弹幕不丢。

**展开**：
- 生产者用 `ObjectProvider<RocketMQTemplate>`（`mq/DanmakuMessageProducer.java:29`），`available()` 判断开关与 Bean 是否存在（`:42-43`）；
- `send()` 返回 boolean，失败时 `FlushTask` 走 `dispatchLocally()`（`DanmakuFlushTask.java:124-132`）；
- 消费端 `@ConditionalOnProperty(name="danmaku.mq.enabled")`（`mq/DanmakuMessageConsumer.java:26`），关闭时连监听器都不注册；
- 默认 `danmaku.mq.enabled: false`（`application.yml:51`），compose 演示时置 `true`（`docker-compose.yml:438`）。

### Q15 为什么选 RocketMQ 不选 Kafka？

**一句话**：吞吐够用就行，Kafka 的分区/副本/KRaft 运维成本对毕设是纯负担；RocketMQ 与 Spring Cloud Alibaba 同生态，版本由 BOM 统一管，还自带延迟消息。

**展开**：详细对比表与决策过程见 `docs/实验报告-MQ选型.md` §3–§4（含 RabbitMQ、Redis Stream 的对比与「为什么不用」）。

### Q16 搜索为什么有两套实现（MySQL vs ES）？

**一句话**：默认走 MySQL + Bangumi 聚合，保证零额外依赖可运行；ES 版本用于演示全文检索与相关性加权，可通过改网关路由切换。

**展开**：
- 默认：`SearchController` 先 MySQL `LIKE` 按评分排序，再补 Bangumi 远程结果（`abc-anime-service/.../SearchController.java:29-72`）；
- ES：索引 `abc_anime`，字段加权 `title^3 + tags^2 + description`，见 `abc-search-service`；
- 论文里这是天然的对比实验：召回率、相关性、（如果测了）查询延迟。

## 四、AI 与业务

### Q17 AI 桌宠是怎么实现的？会不会瞎编？

**一句话**：LangChain4j 调 DeepSeek 的 OpenAI 兼容接口做 SSE 流式输出，Prompt 里注入「用户画像 + 检索到的番剧候选」来压制幻觉，并且要求「推荐必须给理由」。

**展开**：
- 上下文来自 Feign 调用户服务取观看历史/收藏（`abc-ai-service/src/main/java/com/abc/aiservice/feign/UserFeignClient.java`），再加本地检索的番剧候选（`AiChatService.java:398` 附近拼「番剧候选」段）；
- Prompt 约束在 `AiChatService.java:69`：「推荐番剧时给出理由，并结合【用户画像】说明为什么适合对方」；
- 会话与会话消息落 MySQL（`sql/ai_chat.sql` 的 `ai_chat_session` / `ai_chat_message`），可回放、可追责；
- 局限（主动说）：不是真 RAG 向量检索，是「关键词 + 候选注入」，没有 embedding 库；**这是诚实的边界**。

### Q18 用户的大模型 API Key 怎么存的？

**一句话**：加密后存用户服务，AI 服务通过 Feign 取用，前端只拿到掩码。

**展开**：
- 接口 `/api/user/ai-settings`、`/api/user/ai-key`、`/api/user/ai-key/raw`（`abc-user-service/.../UserController.java:179-208`）；
- `raw` 接口只应内部调用，网关已对 `/api/user/**` 做鉴权；加固方向是给 `raw` 加内部令牌。

### Q19 跨服务一致性怎么保证？有没有分布式事务？

**一句话**：没有引入 Seata 这类分布式事务，采用「最终一致 + 幂等 + 补偿」的工程做法，因为业务上大多数场景允许短暂不一致。

**展开**：
- 弹幕：Redis 缓冲 → 批量落库 → 广播，落库失败不广播（宁可少广播，不可查不到）；
- 计数类（播放量、热搜）：Redis 计数，允许与 MySQL 短暂不一致，定时/触发式回写；
- 真正需要强一致的只有「扣减/支付」类，本项目没有；答辩时说明「技术选型要匹配业务，不为了用而用」。

### Q20 限流、熔断、链路追踪做了吗？

**一句话**：部分做了——弹幕服务有业务级限流与去重，网关有黑名单与角色校验；Sentinel 熔断限流、SkyWalking 链路追踪**没做**，属于明确列出的后续工作。

**展开**：别答「不需要」，答「优先级」：
- 已做：业务限流（`DanmakuRateLimiter`）、去重、网关统一鉴权、Feign 超时配置；
- 没做：Sentinel 的 QPS 限流/熔断降级、分布式链路追踪、统一日志聚合；
- 理由：毕设周期内优先保证「核心链路可演示 + 可压测」，这两项在 roadmap 里排 P1；如果问「怎么加」，答：网关引入 `spring-cloud-starter-alibaba-sentinel` + 控制台，按路由配 QPS 阈值与降级返回。

## 五、测试与工程化

### Q21 性能测试怎么做的？瓶颈在哪？

**一句话**：JMeter 两套脚本（REST 链路 + 弹幕 WebSocket），三档并发，改造前后对照；瓶颈主要在单房间广播的 N² 扇出与单实例消费。

**展开**：
- 脚本与用法：`jmeter/README.md`，执行 `jmeter/run.ps1 -Scenario all -Levels 200,500,1000`；
- 指标口径（TPS/P95/错误率定义）与对照实验设计：`docs/实验报告-压测对比.md` §4–§6；
- 逃生回答：如果被问「数据呢」——如实说「脚本已就绪，本机未装 JMeter 未实跑；论文定稿前补齐」，并现场展示 `.jmx` 的线程组与断言配置。

### Q22 这个项目最大的亮点和最大的不足分别是什么？

**亮点（挑两条讲，别一口气全说）**：
1. **弹幕写路径的工程化改造**：从「onMessage 同步写库 + 同步广播」到「Redis 缓冲 + 批量落库 + 可选 MQ + 独立广播线程池 + 限流去重屏蔽」，同时 MQ 做成可插拔、失败自动降级——有设计、有实现、有压测方案；
2. **规则化视频源引擎**：把「换源」抽象成可配置的 CSS/XPath 规则，支持在线测试与外部规则导入，解决了第三方站点改版就要改代码的问题。

**不足（主动列，显得可信）**：
1. 未接入 Sentinel 熔断限流与链路追踪；
2. 服务端口直接暴露，内部调用无令牌校验；
3. AI 模块没有真正的向量检索；
4. 未引入 Seata，跨服务一致性靠最终一致 + 业务容错；
5. 压测只做了单机单实例，未验证水平扩展。

**收尾话术**：「如果再多两周，我会优先补 Sentinel + 链路追踪 + 推荐服务，这三块对『答辩可展示』和『简历可讲』收益最高。」
